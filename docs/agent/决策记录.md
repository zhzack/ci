# Mini Pipeline 技术决策记录 (ADR)

本文档记录 `Mini Pipeline` 架构演进过程中所做出的**重大技术决策**及决策背景与权衡理由。日常细微代码调整与常规 Bugfix 不计入本文档。

---

## 决策 1：插件协议采用“无侵入标准进程（Zero SDK）”，而非专用 SDK

- **决策时间**：Phase 1 设计期
- **决策内容**：
  平台执行的插件只要求是一个操作系统级可执行文件（Shell 脚本、Python 脚本、Node.js 文件或可执行二进制文件）。平台通过约定好的目录布局（`workspace/input/`, `workspace/output/`）以及结构化 JSON（`context.json`, `params.json`, `input.json`, `output.json`）向插件传递数据与收集结果。
- **为什么这么做**：
  1. **零学习成本与多语言友好**：用户无需学习、引用任何专有语言包或特定版本的 SDK，任何能在终端里跑通的脚本/工具（curl、ffmpeg、pytest、自研 CLI）都能直接封装为插件；
  2. **避免依赖地狱（Dependency Hell）**：SDK 方案经常引发 SDK 本身的依赖库与插件运行环境产生版本冲突；
  3. **环境隔离与解耦**：将资源输入（下载文件、解析参数、拉取上游产物）和产物回传的工作全部交由平台承揽，插件编写者只需关注核心业务逻辑。

## 决策 2：调度引擎采用双线程池设计（Coordinator 与 Task Worker 分离）

- **决策时间**：Phase 1 调度设计期
- **决策内容**：
  系统内部划分两个互相独立的线程池：
  - `coordinator_workers`（默认 2 个线程）：专职推进流水线的 DAG 拓扑状态、表达式解析、判断入度并标记就绪；
  - `task_workers`（默认 4 个线程）：专职拉起并监控具体步骤的插件进程执行、收集日志与产物。
- **为什么这么做**：
  在单线程池模型下，如果同时并发提交了大量流水线，每个协调器（Coordinator）在等待其子步骤执行完成时若霸占工作线程，很快会导致整个线程池被“正在等待子任务完成的父任务”占满，而真正的子步骤（Task）排队无法获得执行线程，引发**全局活锁/饿死死锁**。双池设计在资源层面从根本上杜绝了这一隐患。

## 决策 3：远程执行主通信方案采用“Pull 模型（Agent 长轮询）”，辅以 SSH 推模式

- **决策时间**：Phase 2 (0.3.0) 多机设计期
- **决策内容**：
  分布式多机执行采用两种模式分流：
  - **主力模式：Pull 模型 Runner Agent**。由目标机器上的 Agent 进程主动向服务端建立出站 HTTPS 长轮询领任务、回传心跳、上报状态和日志。
  - **补充模式：SSH 直连直推**。由平台保管凭证，通过 Paramiko 直连目标主机建立 SSH/SFTP 执行。
- **为什么这么做**：
  1. **网络拓扑穿透（NAT 友好）**：在真实企业与个人开发场景中，开发者的笔记本、内网测试服务器大多位于企业防火墙、VPN 或家庭路由器 NAT 之后，中心服务器根本无法主动连接目标机内网 IP，唯有出站连接能够稳定穿透；
  2. **安全性与免提权**：如果平台全量强制使用 SSH 登录目标机，平台必须存储大量高权限 SSH 密码/私钥，存在凭证泄漏风险；而 Pull 模式的 Agent 仅持有一枚低权限任务 Token，失窃风险极低；
  3. **SSH 模式的定位补全**：针对某些不可安装 Python 环境或不允许驻留后台 Daemon 的核心 bastion/跳板机，SSH 模式作为免客户端推模式提供无缝纳管手段。

## 决策 4：任务防重复认领采用“数据库行级条件更新”，不引入 Redis

- **决策时间**：Phase 2 (0.3.0)
- **决策内容**：
  多个 Runner Agent 并发认领任务时，平台直接依托数据库的原子条件更新语义：
  `UPDATE task_runs SET status='RUNNING', machine_id=... WHERE id=... AND status='QUEUED'`。在 PostgreSQL 下结合 `FOR UPDATE SKIP LOCKED`，在 SQLite 下利用单库写事务锁。
- **为什么这么做**：
  1. **极简架构与零运维成本**：轻量级流水线平台追求极低部署门槛（单二进制/单 Docker 即可启动运行），引入 Redis 将导致运维复杂度、高可用方案与数据持久化同步成本陡增；
  2. **强一致事务保证**：任务状态变更、流水线状态推进与审计日志记录在一个关系型数据库事务内完成，天然具备强一致性与 ACID 保障，免去分布式事务协调。

## 决策 5：机器存活与故障恢复采用“租约（Lease）+ 独立收割器（LeaseReaper）”

- **决策时间**：Phase 2 (0.3.0)
- **决策内容**：
  远程任务认领后，服务端赋予该任务一个有效租约期（`lease_expires_at`，默认当前时间 + 120 秒）。Agent 在执行期间每隔 15 秒心跳续租一次。后台常驻轻量级协程 `LeaseReaper`，每隔固定周期扫描数据库中 `status='RUNNING' AND lease_expires_at < NOW()` 的超时任务，强制收割标记为 `FAILED`。
- **为什么这么做**：
  1. **避免任务永久悬挂**：当远端 Runner 机器突然断电、断网、系统崩溃、OOM 退出时，传统的长连接往往需要漫长的 TCP Keepalive 才能感知，甚至服务端可能永远收不到中断通知；
  2. **解耦监控与业务主流程**：调度引擎无需维持每台机器的持久长连接上下文，通过数据库租约状态判定，即使服务端自身平滑重启，租约判定机制依旧成立。

## 决策 6：启动即收割孤儿任务（Reap Orphans on Startup）与分支续跑（Branch Run）

- **决策时间**：Phase 1 稳定性治理
- **决策内容**：
  当平台服务端重启时，所有在数据库中仍处于 `PENDING` 或 `RUNNING` 状态的历史运行记录，在系统启动钩子中全部直接判定收割为 `FAILED` 并记录提示信息。断点续跑统一由用户触发“分支运行（Branch Run）”从失败步骤派生新 Run。
- **为什么这么做**：
  由于本地线程池与内存事件总线在进程重启后完全消失，如果不进行启动清理，界面上将永久残留大量状态转圈却永远不会被调度的“僵尸运行”。由于流水线任务强依赖工作区临时状态，暴力断点续跑极易引入脏数据，因此显式标记失败并通过“分支运行”重建工作区是工程上最为清晰且可追溯的方案。

## 决策 7：产物引用不暴露文件系统物理路径，采用不透明 `artifact_id` + ETag 强缓存

- **决策时间**：Phase 1
- **决策内容**：
  API 与前端交互中，所有的产物下载均使用无规律的 UUID（`artifact_id`），服务端拦截任何包含绝对或相对物理路径的直接读取请求。下载响应中强制基于产物 SHA256 哈希计算 `ETag`。
- **为什么这么做**：
  1. **杜绝越权与目录遍历漏洞（LFI/Path Traversal）**：彻底隔绝攻击者通过传入 `../../etc/passwd` 等方式非法探测宿主机敏感文件；
  2. **节省带宽与极速响应**：流水线生成的构建包、镜像、归档文件通常体积庞大，利用内容哈希作为强验证器，当命中浏览器或代理缓存时直接返回 `304 Not Modified`，避免海量网络 I/O。

## 决策 8：机密凭证采用单主密钥派生 Fernet 对称加密，只对 Owner 开放

- **决策时间**：Phase 2 (0.3.0)
- **决策内容**：
  管理员机或个人机保存的 SSH 账号密码、私钥等机密，使用基于配置文件中单主密钥（`security.secret_key`）经 SHA-256 派生出的 Fernet 密钥进行静态落库加密。系统对分配使用该机器的非 Owner 用户提供完整的“凭证屏蔽机制”（运行任务透明解密注入，但任何 API 均拒绝返回明文凭据）。
- **为什么这么做**：
  1. **最小化运维复杂度**：运维人员只需管理并注入一个 `MINI_PIPELINE_SECRET_KEY` 环境变量，无需维护复杂的 KMS 密钥管理服务；
  2. **兼顾多租户安全共享**：平台管理员可将配备特权凭证的构建机授权给普通开发者跑流水线，但普通开发者无法通过扒取控制台或请求 API 窥探到底层的服务器真实登录密码。

## 决策 9：Windows 环境下 Shell Runtime 优先定位 Git Bash 并修正 PATH 注入

- **决策时间**：Phase 2 跨平台适配期
- **决策内容**：
  在 Windows 操作系统中执行 Shell 插件时，系统探测解释器优先搜索 Git 安装路径下的 `bin/bash.exe`（跳过 `C:\Windows\System32\bash.exe`），并在 `ProcessRunner` 启动任何外部进程前，主动将当前 Python 虚拟环境的 `Scripts` 目录前置注入到 `PATH` 环境变量中。
- **为什么这么做**：
  1. **避免命中无效的 WSL 存根**：Windows 默认在 System32 下放置了一个未经配置就会抛出 127 退出码的假 `bash.exe` 存根，直接导致所有 Shell 插件超时挂起；
  2. **屏蔽 Windows 应用商店 Python 存根陷阱**：Windows 默认预装了指向微软应用商店的空壳 `python.exe` / `python3.exe`（退出码 9009，映射到 Bash 表现为退出码 49）。通过在运行时主动将真实 Python 环境前置，彻底杜绝了脚本意外调用到伪存根的问题。

## 决策 10：单指令环境部署端点（`/install`）采用服务端 User-Agent 智能自适应

- **决策时间**：Phase 2 (0.3.0)
- **决策内容**：
  提供统一的安装端点 `GET /install`。服务端解析 HTTP 请求头的 `User-Agent`，如果识别为 `WindowsPowerShell` 或 `pwsh`，则自动响应针对 Windows PowerShell 优化的 `install.ps1`；若识别为 `curl`、`wget` 或非 Windows 环境，则响应针对 Unix/macOS 的 `install.sh`。
- **为什么这么做**：
  1. **极致的用户体验（One-Liner）**：用户在不同机器上部署 Runner Agent 时，无需事先区分操作系统寻找对应脚本 URL，复制同一条自适应指令直接粘贴进终端即可跑通；
  2. **Token 直传静默拉起**：允许通过 Query 参数 `?token=mrt_...` 直传，脚本拉取完成即刻自动在后台配置并激活 Runner，实现“一句指令、即装即用、自动上线”。

## 决策 11：制品仓库与对象存储采用“无 boto3 纯标准库 SigV4”与双驱动抽象

- **决策时间**：Phase 3 (0.3.1)
- **决策内容**：
  制品与通用资产管理（Package Hub）采用双存储驱动抽象（`StorageDriver`）：
  1. **本地驱动（LocalStorageDriver）**：用于单机部署、私有局域网共享，配合严格的 `is_relative_to(root)` 防跨目录隔离与临时文件原子写入；
  2. **对象存储驱动（S3StorageDriver）**：支持 AWS S3、MinIO、阿里云 OSS、腾讯云 COS、Cloudflare R2，使用纯 Python 标准库（`hmac`, `hashlib`, `urllib.parse`）与现存 `httpx` 实现 AWS SigV4 规范，**不引入额外的庞大 `boto3`/`botocore` 依赖包**。
- **为什么这么做**：
  1. **容器镜像与安装包极简化**：`boto3` 及其依赖（`botocore`, `jmespath`, `s3transfer` 等）体积高达数十兆字节，且更新频繁；而 S3 常用操作（ListObjectsV2, GetObject, PutObject, DeleteObject, HeadObject）仅需简单的 REST + SigV4 签名，使用标准库 + httpx 实现能够将系统依赖和 Docker 镜像体积控制在最小；
  2. **多云对象存储完全兼容**：目前主流云厂商（AWS, MinIO, 阿里 OSS, 腾讯 COS, 华为 OBS, 百度 BOS, 各种 S3-compatible 网关）均严格兼容标准 S3 SigV4 签名与 XML List 格式，统一接入只需一个端点 URL + AccessKey / SecretKey 即可开箱即用；
  3. **资产管理与流水线生态打通**：通过 `publish_as_plugin` 桥梁，用户上传的插件 ZIP 或文件夹可以直接转化为平台插件中心的版本记录，避免“先上传文件再另寻插件发布入口”的割裂体验。

# Mini Pipeline 非源码生产部署与运维指南

本指南面向**发布人员**与**运维人员**，详细说明如何在**不交付任何业务源代码**的前提下，将 Mini Pipeline CI 系统安全、标准、高效地交付并部署至单台或多台生产服务器。

---

## 1. 交付物构成与架构

在非源码交付模式下，运维人员**不需要**获取 Python 或 React 源代码，也**不需要**在服务器安装 Node.js、Python 或构建工具。只需获取以下打包物：

### 交付包目录结构 (`mini-pipeline-release-0.3.0/`)
```text
mini-pipeline-release-0.3.0/
├── docker-compose.yml              # 生产编排文件（引用预构建镜像，无 build 阶段）
├── .env.example                    # 环境变量配置模板
├── deploy.sh                       # Linux / macOS 一键安装与启动脚本
├── deploy.ps1                      # Windows 一键安装与启动脚本
└── mini-pipeline-images-0.3.0.tar.gz  # (可选) 离线全量镜像包（离线纯内网交付时提供）
```

---

## 2. 研发团队：产物打包与交付流程

研发人员在交付给运维前，需在打包机或 CI 流水线上生成产物。

### 方式 A：离线镜像包交付（适合无外网隔离内网）
运行项目内置打包脚本：
```bash
python scripts/package_release.py --version 0.3.0 --include-images
```
脚本会自动完成：
1. 构建 `ci-api:0.3.0` 与 `ci-frontend:0.3.0` 生产镜像；
2. 导出包含 API、前端 Nginx、PostgreSQL 16 的离线压缩镜像 `mini-pipeline-images-0.3.0.tar.gz`；
3. 将部署脚本、编排配置和镜像整合成 `dist_release/mini-pipeline-release-0.3.0.zip`。

*直接将生成的 `.zip` 包发给运维人员即可。*

### 方式 B：企业私有镜像仓库交付（推荐，适合可访问内部 Harbor / ACR）
研发在 CI 流水线中将镜像推送至企业私有仓库：
```bash
# 打标签并推送到私有仓库
docker tag ci-api:0.3.0 harbor.company.com/ci/ci-api:0.3.0
docker tag ci-frontend:0.3.0 harbor.company.com/ci/ci-frontend:0.3.0
docker push harbor.company.com/ci/ci-api:0.3.0
docker push harbor.company.com/ci/ci-frontend:0.3.0
```
交付给运维时，无需附带庞大的镜像 Tar 包，只需交付 `deploy/` 目录中的文件，并在 `.env` 中指定：
```ini
IMAGE_REGISTRY=harbor.company.com/ci/
APP_VERSION=0.3.0
```

## 3. 服务器环境要求与前置检查

| 资源项 | 最低要求 | 推荐配置（生产单机） | 推荐配置（分布式集群） |
| :--- | :--- | :--- | :--- |
| **操作系统** | Linux (Ubuntu 20.04+, CentOS 7.9+, Debian 11+) 或 Windows Server 2022 | Ubuntu 22.04 LTS | 控制台 Linux / 执行机跨平台 |
| **CPU** | 2 核 | 4 核 + | 控制台 4 核，Worker 节点 8~32 核 |
| **内存** | 4 GB | 8 GB + | 控制台 8 GB，Worker 节点 16~64 GB |
| **磁盘存储** | 20 GB 空闲 | 100 GB + 高性能 SSD | 控制台 100 GB，Worker 节点 500 GB+ |
| **软件依赖** | Docker Engine 24.0+，Docker Compose v2.20+ | Docker Engine 26.0+ | Docker Engine 26.0+ |
| **开放端口** | 80 (Web), 8000 (API) | 80, 443, 8000 | 控制台需开放 80/443, 8000 给 Worker |

## 4. 场景一：单台服务器全栈部署（All-in-One 单机生产）

适合中小型团队或并发任务量在单机能力范围内的场景。前端 Nginx、后端 API 与 PostgreSQL 统一运行在一台主机中。

### 步骤 1：上传并解压交付包
运维人员将交付包上传至目标服务器（例如 `/opt/mini-pipeline`）：
```bash
mkdir -p /opt/mini-pipeline && cd /opt/mini-pipeline
unzip mini-pipeline-release-0.3.0.zip
```

### 步骤 2：执行一键部署脚本
* **Linux / macOS 环境**：
  ```bash
  chmod +x deploy.sh
  ./deploy.sh
  ```
* **Windows PowerShell 环境**：
  ```powershell
  .\deploy.ps1
  ```

> [!NOTE]
> `deploy.sh` / `deploy.ps1` 脚本会自动完成以下操作：
> 1. 检测本地离线镜像并自动执行 `docker load` 导入；
> 2. 若无 `.env`，自动从 `.env.example` 创建，并利用系统安全随机源生成 32 位的 Admin Token、Reader Token 及加密密钥；
> 3. 自动执行 `docker compose up -d` 后台启动服务并校验健康状态。

### 步骤 3：验证访问与初始化管理员
1. **健康检查探针**：
   ```bash
   curl http://127.0.0.1/health
   # 应返回: {"status":"ok","version":"0.3.0",...}
   ```
2. **访问 Web 控制台**：
   在浏览器中打开服务器 IP：`http://<服务器IP>`。
3. **初始化管理员账户**：
   系统遵循安全原则，**首个注册的用户将自动获得超级管理员（Admin）权限**。
   运维人员注册首个管理账号后，可在【用户管理】（Users）中根据需要关闭开放注册。

## 5. 场景二：跨多台服务器分布式部署（高可用与大规模并发）

在企业级部署中，通常将**Web & 控制调度中心**、**生产数据库**以及**任务执行机集群**分离。

### 架构拓扑

```
                           【 业务团队 / 开发者 】
                                      │  HTTP (80/443)
                                      ▼
             ┌─────────────────────────────────────────────────┐
             │ 主服务器 A (192.168.1.10)：Web 网关与控制台      │
             │  • ci-frontend (Nginx 端口 80/443)              │
             │  • ci-api      (调度编排、认证授权、WebSocket)    │
             └───────────────┬─────────────────┬───────────────┘
                             │                 │
             SQL 连接 (5432) │                 │ 分发流水线任务 (HTTP / SSH)
                             ▼                 ▼
   ┌───────────────────────────────────┐   ┌───────────────────────────────────┐
   │ 数据库服务器 B (192.168.1.20)      │   │ 任务执行机集群 (Worker Nodes)     │
   │  • 云托管 PostgreSQL 16 (RDS)      │   │  • Worker 1 (Linux 构建机)        │
   │    或独立自建 PostgreSQL 集群      │   │  • Worker 2 (Windows 编译机)      │
   │                                   │   │  • Worker 3 (GPU/测试机)...       │
   └───────────────────────────────────┘   └───────────────────────────────────┘
```

### 1. 接入独立数据库（服务器 B）
1. 在服务器 B 安装 PostgreSQL 16，并创建数据库：
   ```sql
   CREATE USER mini_pipeline WITH PASSWORD 'YourStrongPassword';
   CREATE DATABASE mini_pipeline OWNER mini_pipeline;
   ```
2. 在服务器 A 的 `.env` 中配置实际数据库地址：
   ```ini
   DATABASE_URL=postgresql+psycopg://mini_pipeline:YourStrongPassword@192.168.1.20:5432/mini_pipeline
   ```
3. 在服务器 A 的 `docker-compose.yml` 中，将 `database` 服务注释或删除，`api` 服务即可直接连接独立数据库。容器启动时会自动通过 Alembic 执行数据表迁移。

### 2. 横向挂载多台任务执行机（Worker Nodes）
Mini Pipeline 具备**弹性分布式调度底座**，控制台服务器只负责派发指令，重型任务一律由 Worker 节点执行。

运维无需手动修改服务端配置，只需将各台 Worker 机器接入：

#### 方案一：Agent 自动拉取模式（推荐，支持跨防火墙）
1. 管理员登录控制台，进入【机器管理】（Machines）页面；
2. 点击【添加机器】-> 选择【管理员共享机】（Admin Pool）；
3. 连接模式选择【Agent 拉取模式】，复制单指令至 Worker 机器终端执行：
   * **Linux / macOS Worker**：
     ```bash
     curl -fsSL http://192.168.1.10/install?token=mrt_xxxxxxxxxx | sh
     ```
   * **Windows Worker**（管理员 PowerShell）：
     ```powershell
     irm http://192.168.1.10/install?token=mrt_xxxxxxxxxx | iex
     ```
   *说明：Agent 自动后台常驻、开机自启，每 15 秒通过出站 HTTP 长轮询控制台认领任务，无需在 Worker 开放任何入站端口。*

#### 方案二：SSH 直连推送模式（免装 Agent）
1. 在【机器管理】页面点击【添加机器】；
2. 连接模式选择【SSH 直连】；
3. 输入 Worker 节点的 SSH IP、端口、登录用户名与密码（或私钥）；
4. 点击【测试连通性】，系统测试成功后即可直接通过 SSH 下发执行任务包并拉回日志。

## 6. 日常运维、备份与平滑升级

### 1. 数据持久化位置
所有系统关键状态均通过 Docker 卷进行持久化，容器销毁不会丢失数据：
* `postgres-data`：PostgreSQL 生产数据库表数据。
* `pipeline-data`：对应容器内 `/app/data`，存放插件包缓存、任务历史日志及归档产物。

### 2. 生产数据库日常备份
运维可在宿主机添加定时 crontab 任务，执行逻辑备份：
```bash
# 备份命令（单机容器环境）
docker compose exec -T database pg_dump -U mini_pipeline mini_pipeline | gzip > /opt/backup/db_$(date +%Y%m%d_%H%M%S).sql.gz

# 恢复命令
gunzip -c /opt/backup/db_20260830_000000.sql.gz | docker compose exec -T database psql -U mini_pipeline mini_pipeline
```

### 3. 平滑升级流程（保留现有数据）
当研发团队发布新版本（例如 `0.4.0`）时，运维升级步骤如下：
```bash
# 1. 导入新版本镜像（离线包或拉取镜像）
docker load -i mini-pipeline-images-0.4.0.tar.gz

# 2. 修改 .env 中的版本号
sed -i 's/APP_VERSION=0.3.0/APP_VERSION=0.4.0/g' .env

# 3. 平滑拉起新版本容器
docker compose up -d

# 容器启动时会自动执行 alembic upgrade head 完成数据库表结构平滑升级，无需手工执行 SQL！
```

### 4. 故障回滚流程
如新版本出现非预期异常需要回退：
```bash
sed -i 's/APP_VERSION=0.4.0/APP_VERSION=0.3.0/g' .env
docker compose up -d
```

## 7. 常见故障排查（Troubleshooting）

| 现象 | 可能原因 | 排查与解决办法 |
| :--- | :--- | :--- |
| 启动时 API 容器报错 `MINI_PIPELINE_ADMIN_TOKEN in .env` 退出 | 未配置环境变量三件套 | 检查 `.env` 文件是否存在且包含了三个安全密钥参数 |
| 前端页面打不开（Connection Refused） | 端口占用或防火墙阻断 | 检查防火墙是否放行 80 端口，或通过 `.env` 中 `FRONTEND_PORT=8080` 更换端口 |
| 外部 Worker 机器无法连接控制台 | 控制台网络未开放入站访问 | 确保控制台服务器的 80 端口允许 Worker 节点的 IP 访问 |
| 实时任务日志加载慢或不更新 | 外部企业 Nginx 开启了缓存 | 在最外层反代中加入 `proxy_buffering off;` 以支持 SSE 事件流实时刷新 |
